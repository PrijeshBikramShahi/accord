# Accord — MVP plan

Planning baseline: 10 October 2026. React/TypeScript + Node/TypeScript; newer to AWS; 2–3 weeks at 10–15 hours/week; $50 AWS Academy Learner Lab credit. This document is a proposal, not an implementation or a claim that lab access has been verified.

**1. Product promise and scope**

Accord helps a freelancer compare client feedback with the agreed project scope, inspect supporting evidence, and record a human decision. A successful demonstration follows one request all the way from client feedback to a revision task or an explicitly approved scope change.

Target the upper end of the available time: **three weeks × 15 hours = 45 hours**. This is a tightly scoped portfolio release, with AWS setup the largest schedule uncertainty. At 20 hours, target the manual portal workflow; do not claim a completed AI MVP. Keep a running timebox and cut presentation polish before reliability or isolation checks.

| Build in the MVP | Boundary |
|---|---|
| One freelancer, multiple isolated projects | Seed one owner and two client accounts across two projects. No public signup, invitation email, teams, or billing. |
| Versioned briefs | Plain text with stable paragraph IDs. Draft → submitted → approved. Every edit creates a version. |
| Deliverables | Title, description, acceptance criteria, status, optional private attachment. Simple list, no board or dependencies. |
| Client feedback | Append-only comments on a deliverable or project; corrections are new comments referencing the original. |
| Private attachments | PDF, PNG/JPEG, or plain text; max 5 MB/file and 20 files/project. Download only; no OCR, extraction, preview engine, or AI attachment processing. Use synthetic files for the demo. |
| Scope analysis | Analyze one feedback thread against the approved brief and approved changes. Classify each requested item separately. |
| Human review | Accept/edit/reject advice; create revision tasks, draft a change request, or draft a clarification. Explicit human action publishes anything to the client. |
| Approval history | Client approval of a submitted brief, deliverable, or change request binds to an exact version. |
| Background job status | Pending, running, complete, failed, stale; retry and recovery visible to the freelancer. |

Defer brief-to-plan generation, project-memory Q&A, vector search, third-party integrations, notifications, estimates generated by AI, rich text editing, real-time updates, and production customer onboarding. Revisit secondary AI features only after the core workflow passes its evaluation and cost gates.

**2. User experience and scope rules**

Use three primary screens: project list; project workspace with Brief, Deliverables, Feedback, and History tabs; freelancer-only scope review. Keep task and change-request details in the workspace rather than building separate management tools.

The default journey:

1. Freelancer creates a project, assigns an existing client, writes a brief and deliverables, and submits brief version 1.
2. The designated client approver reviews and approves that exact version. Drafts and ordinary comments never establish commitments.
3. Client comments on a deliverable: “Please change the export button label, and add scheduled weekly exports.”
4. Freelancer selects **Analyze feedback**. The UI shows a queued job and polls with backoff while open.
5. Review shows separate findings: button-label revision potentially included if the brief supports it; scheduled exports potentially additional; either item unclear if the evidence does not establish enough context. Each finding shows the request, label, short rationale, and clickable versioned quotations.
6. Freelancer edits the proposed actions. Included work can become a revision task. Added scope becomes a draft change request. Missing evidence becomes a clarification draft; the freelancer explicitly posts it as a comment.
7. Freelancer submits a change request containing the concrete scope delta and any manually entered schedule/fee implications. Client approves that exact version. Only then does the scope baseline change and associated added-scope work become actionable.
8. Freelancer completes a task/deliverable; client records deliverable approval. The history explains which feedback and approval authorized the work.

Approval is recorded by the authenticated designated client, with the submitting freelancer's action as a separate event. The freelancer cannot silently approve on behalf of a client. AI cannot publish comments, approve versions, create accepted commitments, or change project permissions.

The effective scope is **the latest approved brief plus approved changes not already incorporated into that brief**. A replacement brief explicitly lists incorporated change IDs; other approved changes remain active. Submission screens show this list to prevent accidental loss or double counting. Conflicting provisions produce “unclear” until a human resolves them. Pending changes and later casual comments are contextual evidence, not agreed scope.

Each project has `scopeRevision` and `contextRevision` counters. Approved scope changes increment both; additions to the analysis-eligible feedback/context increment the latter. Old analyses remain readable with their original evidence, but become stale and cannot directly generate actions until rerun. A manual decision remains possible with its own rationale and audit record.

**3. Provisional architecture**

Choose ordinary React with Vite, TypeScript throughout, a shared runtime schema library such as Zod, and a small Node API organized into domain modules. Pin supported package/runtime versions when implementation starts. Use AWS SAM/CloudFormation only after confirming its deployment permissions and ability to reference the supplied execution role.

```text
React browser ── authenticated HTTP ── API Gateway ── API Lambda
      │                                    │           │
      │                                    │           ├── DynamoDB
      └── short-lived upload/download ── private S3     └── SQS + DLQ
                                                               │
                                                         Worker Lambda
                                                          │         │
                                                     DynamoDB    Bedrock
```

Cognito is the first authentication candidate. API Gateway validates access-token signature/claims and scopes; the API separately checks project membership and allowed actions. Gateway authentication alone is insufficient for project isolation. [AWS JWT authorizer documentation](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-jwt-authorizer.html)

Use two Lambda functions, one application table, one private file bucket, one queue and dead-letter queue, and short-lived logs. Run the frontend locally during development. A hosted frontend using a private static bucket behind CloudFront is optional only if permissions and time permit; a local browser demonstrating a deployed backend is acceptable portfolio evidence. No custom domain is required.

Use one region selected by the lab, DynamoDB on-demand capacity if allowed, ordinary on-demand Lambda execution, and no VPC/NAT gateway. Avoid provisioned model throughput, always-on databases, Kubernetes, and a vector database. Model access sits behind a small provider interface with live and clearly labeled fixture modes. Fixtures test UI/contracts; they do not count as live model quality evidence.

**4. Data model and access patterns**

The tenant is the freelancer workspace; projects are the client-isolation boundary. Keep `workspaceId` even with one active freelancer so tenant ownership is explicit. Resolve workspace and identity from server-side membership, never from an untrusted owner ID in the request.

| Record | Essential fields and invariants |
|---|---|
| Workspace / membership | Workspace ID, user subject, owner role. Seeded configuration for MVP. |
| Project / membership | Workspace ID, project ID, owner, client subject, designated approver, state, scope/context revisions. |
| BriefVersion | Version, text/paragraph IDs, content hash, creator, submitted time, status, incorporated change IDs. Submitted content is immutable. |
| DeliverableVersion | Deliverable ID/version, description, acceptance criteria, status, attachment references. Approvals bind to version. |
| Comment | ID, author, body, deliverable/thread target, created time, optional correction-of ID. Append-only. |
| AttachmentVersion | ID/version, server-issued object key, exact S3 version ID if enabled, size, MIME, checksum, uploader, parent resource, upload state. |
| Approval | Target type/ID/version/hash, actor, approve/reject decision, timestamp. Append-only; corrections are new events. |
| ChangeRequestVersion | Exact scope delta, source feedback/analysis, human-entered implications, submitted version, approval state. |
| RevisionTask | Title, acceptance criteria, status, source finding, authorized scope/approval reference, creation decision ID. |
| AnalysisJob / result | Requester, feedback IDs, frozen source manifest, context/scope revisions, prompt/model versions, state, attempts, lease, findings, usage, timings. |
| ReviewDecision / audit | Actor, chosen action, edited text, rationale, source analysis, target IDs, timestamp, idempotency key. |
| AI budget ledger | Reserved/consumed estimated inference cost, attempt IDs, daily and project limits. |

Suggested DynamoDB layout: project records share `PK = W#<workspaceId>#P#<projectId>` with sort-key prefixes such as `META`, `MEMBER#`, `BRIEF#`, `COMMENT#`, `JOB#`, and `TASK#`. Keep a small per-user project-membership index for listing projects. Recheck the authoritative membership before accessing a project; an index result is not permission.

Primary access patterns are list my projects, load one project's brief/deliverables/history, load one feedback thread, fetch one job, and list pending recovery jobs for a known project. Use key queries with pagination, not table scans. Cap feedback size and source manifests so records remain small; store larger immutable analysis/source bundles privately in S3 if necessary. Do not build generalized search.

Use conditional writes and transactions for approval + revision increment + audit, and for decision + task creation. Persistent application idempotency records are required; do not rely solely on a transaction request token's limited lifetime. [DynamoDB transactions](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html)

**5. API boundaries**

All project routes start with `/projects/{projectId}`; all resource IDs must be resolved inside that authorized project. Returns include resource versions. Use `401` for no valid identity, `404` for inaccessible resources, `409` for stale/concurrent writes, and `422` for invalid content. Paginate list endpoints.

| API group | Representative routes | Permissions / behavior |
|---|---|---|
| Projects | `GET /projects`, `POST /projects`, `GET /projects/{id}` | Only owner creates; list only memberships. Membership seeding replaces an invitation product. |
| Briefs | `GET/POST …/briefs`, `POST …/briefs/{version}/submit` | Owner authors/submits; clients see submitted/approved versions. |
| Deliverables | `GET/POST …/deliverables`, `PATCH …/deliverables/{id}` | Owner manages; updates require expected version. |
| Feedback | `GET/POST …/comments` | Project participants; target resources must belong to project. |
| Files | `POST …/attachments/upload-intent`, `POST …/attachments/{id}/complete`, `GET …/attachments/{id}/download` | Authorize parent; server chooses key; completion verifies object metadata. |
| Analysis | `POST …/analyses`, `GET …/analyses/{id}`, `POST …/analyses/{id}/retry` | Owner only; POST returns durable job ID and `202`, not model output. |
| Review | `POST …/analyses/{id}/decisions` | Owner; validate source freshness and idempotency; create draft CR or accepted revision tasks. |
| Changes | `GET/POST …/changes`, `POST …/changes/{id}/submit` | Owner drafts/submits; clients see submitted versions. |
| Approvals | `POST …/approvals` | Designated client only; exact submitted target/version/hash required. |
| Tasks/history | `GET …/tasks`, `PATCH …/tasks/{id}`, `GET …/history` | Owner updates tasks; clients see shared project records, not internal AI drafts. |

State-changing POSTs carry an idempotency key; writes to existing resources carry an expected version. The server controls actor, timestamps, scope status, object keys, and approval eligibility. Restrict CORS to the chosen frontend origins.

Issue file URLs only after permission checks, expire downloads after about 60 seconds, and bind downloads to immutable versions. Presigned URLs remain usable by their holder until expiry; membership revocation does not retroactively invalidate a previously issued URL. Enforce file size via upload policy and completion verification; use unique upload keys and record the exact accepted version. [S3 presigned URLs](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)

**6. AI processing and reliability**

Direct context is enough for the small demo. Include the complete current approved scope, ordered active approved changes, target feedback thread, and referenced deliverable criteria. Mark each source with type, version, approval status, paragraph IDs, and hash. Include contextual comments only from the same project and label them nonbinding. Private attachments are not model evidence in this release.

Start with a total request cap of roughly 6,000 input tokens and 1,200 output tokens, including instructions/schema. The exact accounting depends on the chosen model. If necessary scope exceeds the input limit, fail with a clear context-too-large status and require a smaller supported project; never silently truncate agreed scope and then call something an addition.

Structured result: `findings[]`, each with request span, one of `likely_included | possible_scope_addition | unclear`, short rationale, `citations[]` containing source ID/version/paragraph/quote, `missingInformation[]`, and proposed action text. Missing pricing, deadlines, and acceptance criteria stay explicitly unanswered. A compound request produces multiple findings; do not force one label for a mixed comment.

Server validation checks schema, enums, size limits, citation source membership, exact quoted text against the frozen source, and required clarification when evidence is missing. A source-existence check does not prove semantic support; human review and the evaluation rubric assess that. “Possible scope addition” cites the relevant baseline boundary and request; absence of an exact matching phrase alone is not proof of exclusion. Reject fabricated citations and invalid output into a reviewable failed state.

Treat all source text as untrusted data. Keep instructions separate, tell the model never to obey instructions inside documents, provide no tools, and run the same validator regardless of model output. A model result cannot execute any write action. Render output as plain text or sanitized Markdown.

Job protocol:

1. API checks permissions, freezes the source manifest, reserves worst-case inference cost, and conditionally creates a job using the request idempotency key.
2. API sends the job ID to SQS. Because saving and sending cannot be one transaction, retain dispatch state. Retrying the same request resends a pending job. Provide an owner-only/operator recovery command for old pending jobs; test a crash between save and send. At this scale documented manual recovery is acceptable; automatic scheduled dispatch recovery is deferred.
3. Worker loads the job, rechecks current requester access, and claims a conditional expiring lease. Already-completed deliveries exit without another model call. A worker losing its lease cannot overwrite a newer result.
4. Worker checks the AI enable flag, attempts remaining, and reserved cost before invocation. If sources already changed, mark stale and request a rerun.
5. Invoke, validate, and save the result with timing, tokens and attempt outcome. On later display/action, compare context and scope revisions again.
6. Human decision transaction checks the same revisions, persists decision/audit, and creates uniquely identified tasks. A duplicate click returns the existing decision; an edited retry with the same key is rejected.

Use batch size 1, bounded worker concurrency, an SDK request timeout below the Lambda timeout, and at most three paid invocation attempts per job across all retries. Retry only transient throttling/timeouts/server errors with bounded backoff; invalid schema or unavailable access is terminal. A crash after model completion but before saving can cause a second paid invocation: promise duplicate-free business actions, not exactly-once model billing.

Configure a DLQ and an explicit job recovery view. Track a job as recoverable/failed after its lease and retry window expire, so the UI does not remain “running” forever. Replaying requires an operator action, valid access, and a fresh budget reservation. SQS/Lambda can deliver duplicates; AWS recommends queue visibility of at least six times the function timeout plus any batch window. The exact concurrency and timeouts belong in the feasibility result. [SQS processing](https://docs.aws.amazon.com/lambda/latest/dg/with-sqs.html), [SQS configuration](https://docs.aws.amazon.com/lambda/latest/dg/services-sqs-configure.html)

**7. Evaluation design**

Create **40 synthetic brief/feedback pairs** before prompt tuning: 14 focused on included revisions, 14 on additions, and 12 on ambiguity. Include several compound requests and annotate every requested item. Cover explicit exclusions, prior approved additions, unapproved proposals, conflicting versions, missing criteria, paraphrases, prompt injection, and irrelevant context.

Split by project scenario into 20 development and 20 locked test cases, with a balanced primary-label distribution of 7/7/6 in each. Do not place paraphrases of the same project on both sides. Each case stores exact source versions, expected item labels, acceptable evidence spans, forbidden invented commitments, and when clarification is required. The developer writes and reviews gold labels; record that this is a small single-annotator synthetic evaluation, not proof of production accuracy.

Allow up to three development runs, then one locked test run after freezing prompt/model/schema: approximately 80 base calls. Review test results afterward; if tuning continues, that set becomes development data and a fresh holdout is needed. Avoid a paid LLM judge; score schema/citation existence automatically and semantic support manually.

| Metric | Provisional acceptance target |
|---|---|
| Three-class classification | Macro-F1 ≥ 0.80 on requested items; show confusion matrix and per-class precision/recall. Unmatched/missed items count as errors. |
| Citation validity | 100% of presented references resolve to the exact allowed source/version. |
| Semantic citation support | ≥95% of evaluated evidence-dependent claims supported by their cited text. Show numerator/denominator. |
| Invented commitments | Zero observed invented promised features, prices, dates, or criteria on the locked set. |
| Clarification | ≥80% recall on items labeled as needing clarification; also report precision and unnecessary clarification rate. |
| Reliability | Invalid result rate and terminal job failure rate reported, never dropped from classification/coverage results. |
| Latency | Report model-only and queued-to-complete median/p95; target <60 seconds p95 on the small test, with sample size and cold starts noted. |
| Cost | Record every attempt; provisional mean target ≤$0.02 per successful analysis including retries, subject to measured model pricing. |

Also run a separate deterministic integration suite: cross-project IDs and S3 URLs; forged approval role; revoked membership before job execution; duplicate SQS delivery; duplicate human decision; worker crash; save/send gap; invalid citations; concurrent scope approval; stale analysis; and exhausted budget. Add a second synthetic workspace to isolation tests even though the product demo has one freelancer.

These are targets, not promised results. If quality misses the gate, keep the portal usable with manual decisions and label the live AI feature experimental. Fixture responses cannot satisfy the live AI evaluation gate.

**8. AWS feasibility gate — before infrastructure commitment**

Timebox to 3–4 hours at the start of implementation. Record each item as verified, denied, or not tested, with date, region, redacted evidence and fallback. No account-specific permission has been checked in this planning session.

| Check | Required proof / fallback |
|---|---|
| Lab boundaries | Read the actual course/Learner Lab service list, allowed regions, session expiry, resource persistence/reset behavior, remaining balance, credit coverage and expiration date. Public AWS docs do not establish this lab's entitlements. |
| Credentials and roles | Identify the supplied execution role, role trust, permitted `iam:PassRole`, and policies. Do not assume role creation is allowed. Parameterize existing role ARNs; avoid requiring CDK bootstrapping or IAM-policy changes. |
| Deployment | Confirm CloudFormation/SAM create/update/delete and deployment-artifact bucket access. Inspect generated resources for forbidden role creation. If denied, document the block and use local demo mode; do not call manual console setup reproducible deployment. |
| API/data/files | Smoke-test intended API Gateway type, Lambda runtime, DynamoDB conditional transaction, S3 private upload/read/version access, CORS, and role permissions. Remove probes afterward. |
| Background jobs | Verify SQS, DLQ, event-source mapping creation, worker permissions and the ability to configure limits. If denied, use the same job contract with a local worker; disclose that cloud queue reliability is unverified. |
| Authentication | Verify Cognito user pool/app client creation, demo users and an authenticated browser-to-API request. If blocked, use an existing allowed OIDC issuer only if already available; otherwise remain local. Do not replace identity with a public role selector. |
| Bedrock | Check model-region compatibility, invocation permissions, any provider/account activation, and credit applicability. Make a tiny priced invocation from the actual worker role and repeat after activation settles. Model listing is not invocation proof. Do not opt into Marketplace purchases without confirming lab permission and funding. |
| Monitoring/cost | Verify log writes, retention control, billing visibility, lab balance, budget alerts if permitted, and data available for actual cost reconciliation. |
| Cleanup | Verify delete permissions and treatment of retained/versioned resources, then demonstrate removal of the probe stack. |

Bedrock model access can depend on Marketplace permissions, provider prerequisites, account eligibility and region; activation can behave differently from steady-state access. These checks must be made in this lab. [AWS model access documentation](https://docs.aws.amazon.com/bedrock/latest/userguide/model-access.html)

Decision: if the core services and inference pass, use the proposed AWS architecture. If only inference fails, ship the manual AWS portal plus labeled replay demonstrations, and explicitly leave the applied-AI/live-evaluation milestone incomplete. External APIs require separate funding; they are not an automatic fallback. Local inference is an optional later feasibility test if suitable hardware/model access already exists, not a new requirement for this timebox.

**9. Budget and operational limits**

Treat $50 as the ceiling, not the spending target. Plan to finish ordinary development below $25, preserve $10 for fixes/cleanup, and keep the final $15 unused as protection against delayed accounting. If the lab balance is already below $50, reduce these envelopes proportionally before any deployment.

| Envelope | Planning allowance, not a price quote |
|---|---:|
| Model probes, development evaluation and demo inference | $10 |
| API, Lambda, DynamoDB, SQS, S3, logs and optional hosting | $10 |
| Deployment experiments | $5 |
| Fixes and cleanup reserve | $10 |
| Unused buffer | $15 |

Choose the model only after access and price verification. Estimate inference as `(input tokens × input price per million + output tokens × output price per million) / 1,000,000`, summed over attempts. For illustration only, prices of $1/M input and $4/M output with 6,000 input + 1,200 output tokens mean $0.0108 per call, or $3.24 for 300 calls. These are hypothetical rates, not a quotation for an accessible Bedrock model. Use the chosen model/region's current [Bedrock pricing](https://aws.amazon.com/bedrock/pricing/) before reserving spend.

Set a maximum of 300 paid attempts across experiments, tests and demos, plus an inference dollar ceiling of $10; whichever is reached first stops calls. A serialized/conditional ledger reserves worst-case cost before each attempt, including retries. Keep uncertain timeout attempts charged against the allowance until reconciled. Count all manually invoked experiments too.

Other limits: AI available only to the seeded owner; 30 attempts/day by default; one active analysis per project; bounded worker concurrency; 1 GB total stored demo assets; seven-day log retention; no full prompts, tokens, credentials or file URLs in logs. Use structured request/job IDs, counts, timings, failure reasons, and estimated cost. Record infrastructure request/duration/storage quantities and a dated regional rate snapshot, then compare estimates against available billing evidence. Do not assume free-tier eligibility for a Learner Lab.

At $25 observed spend, stop feature expansion and capture evidence; at $35, disable new AI and begin cleanup. Maintain an immediate server-side AI kill switch. These application limits protect inference, not all AWS charges. AWS budget alerts are delayed and are not a hard spending cap, so check the lab balance each work session and reconcile after cleanup. [AWS Budgets limitations](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-managing-costs.html)

**11. Definition of done and durable portfolio evidence**

- [ ] Two client identities complete the demo and cannot read, write, download, approve, or invoke analysis against each other's projects; a cross-workspace test also passes.
- [ ] Client feedback yields separately cited findings; the freelancer can inspect evidence, override advice with a reason, and explicitly create the appropriate human-approved action.
- [ ] Approved scope changes and deliverable approvals bind to immutable versions; drafts never silently alter scope.
- [ ] Replay/duplicate requests do not duplicate tasks or approvals; stale analysis and concurrent changes are rejected safely.
- [ ] Pending dispatch, transient failures, terminal failures and DLQ recovery have been exercised and documented.
- [ ] Live model evaluation and cost/latency evidence meet the chosen targets, or limitations are clearly reported and the AI feature remains experimental.
- [ ] Source, lockfile, infrastructure template, nonsecret configuration example, seed data and deploy/cleanup instructions permit a fresh supported-lab deployment. Lab credentials are never committed.
- [ ] A reviewer can see the workflow without the expired lab: short recorded walkthrough, screenshots, architecture, API contract, schema examples, evaluation cases/results, sanitized failure evidence and estimated-versus-observed cost report.
- [ ] Offline fixture replay is visibly labeled “recorded/fixture output,” includes provenance where applicable, and does not imply live inference or current cloud availability.
- [ ] Cleanup removes project stacks, queues, log groups, deployment artifacts and all file versions/delete markers after evidence export; retained resources are checked explicitly. Verify no project resources remain and check delayed billing later. Deleting only the latest key in a versioned bucket does not erase older versions. [S3 version deletion](https://docs.aws.amazon.com/AmazonS3/latest/userguide/DeletingObjectVersions.html)

The strongest portfolio story is a small, inspectable system: clear client boundaries, an honest approval history, useful AI suggestions with evidence, and measured failure/cost behavior. Live AI, AWS deployment, and offline replay should each be labeled according to what was actually verified.
